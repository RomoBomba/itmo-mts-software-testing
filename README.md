# Нагрузочное тестирование REST API в JMeter и Gatling

В работе проверяется, как локальный REST API отвечает на запросы при нагрузке 10, 25 и 50 виртуальных пользователей. Для каждого уровня выполнены отдельные запуски JMeter и Gatling, сохранены результаты и HTML-отчёты. Сценарии обращаются к одному API и используют одинаковые данные и паузу между запросами.

## Окружение

- macOS, архитектура arm64.
- Microsoft OpenJDK 21.0.12.1.
- Apache JMeter 5.6.3.
- Gatling 3.16.0, запуск через Maven-плагин 4.21.12.
- Для запуска Gatling нужен Maven.
- Сервер и генераторы нагрузки запущены на одном компьютере. JMeter и Gatling запускались по очереди.
- На сервере используется пул из 8 потоков.

## Тестируемый API

Для эксперимента используется собственный локальный сервер на Java. Его код находится в [LocalApiServer.java](src/main/java/ru/itmo/testing/local/LocalApiServer.java). Сервер доступен только на `127.0.0.1:8080`, возвращает данные из памяти и не обращается к базе данных или внешним сервисам.

Запрос для получения товара:

```text
GET http://127.0.0.1:8080/api/products/{id}
```

Доступны товары с идентификаторами от 1 до 5. Например, запрос `/api/products/1` возвращает HTTP 200 и JSON:

```json
{"id":1,"name":"Product 1","price":100}
```

Для неизвестного идентификатора сервер возвращает HTTP 404, для метода, отличного от GET - HTTP 405.

## Сценарий JMeter

Сценарий сохранён в [jmeter/products.jmx](jmeter/products.jmx). На каждой итерации виртуальный пользователь получает идентификатор из CSV, ждёт 1 секунду и отправляет запрос к API.

| Элемент | Настройка |
|---|---|
| Thread Group | Число пользователей, ramp-up и длительность задаются через параметры CLI |
| HTTP Request — Get product | GET `/api/products/${id}` на `127.0.0.1:8080` |
| CSV Data Set Config — Product IDs | Чтение идентификаторов из `products.csv` |
| Response Assertion — Status is 200 | Проверка, что код ответа равен 200 |
| Constant Timer — Think time 1 second | Пауза 1000 мс перед каждым запросом, включая первый |
| View Results Tree | Использовался для отладки, отключён перед нагрузочными запусками |

Данные находятся в [jmeter/products.csv](jmeter/products.csv):

```csv
id
1
2
3
4
5
```

Первая строка задаёт имя переменной `id`. В CSV Data Set Config включено повторное чтение файла после последней строки (`Recycle on EOF = True`), остановка потока при окончании файла отключена. Режим `All threads` означает, что пользователи читают общий набор данных.

Путь к CSV указан относительно файла сценария. Для запуска не нужно менять пути внутри `.jmx`. Авторизация и дополнительные заголовки для этого API не требуются.

Перед основными запусками сценарий проверен в GUI: один пользователь выполнил пять итераций, получил пять разных товаров, все запросы завершились со статусом 200.

## Профиль нагрузки

Запуски выполнены последовательно в режиме CLI. Между ними менялось только число пользователей. Запрос, набор данных, ramp-up, длительность и пауза оставались одинаковыми.

| Запуск | Пользователи | Ramp-up, с | Длительность, с | Пауза перед запросом, мс |
|---|---:|---:|---:|---:|
| 1 | 10 | 10 | 120 | 1000 |
| 2 | 25 | 10 | 120 | 1000 |
| 3 | 50 | 10 | 120 | 1000 |

Пользователи подключались постепенно в течение первых 10 секунд. Этот период входит в общую длительность запуска. Итерации повторялись до окончания заданного времени. При ошибке запроса сценарий продолжал работу, чтобы ошибка попала в результаты.

Параметры Thread Group:

- Number of Threads: `${__P(users,1)}`.
- Ramp-up period: `${__P(rampup,1)}`.
- Loop Count: Infinite.
- Specify Thread lifetime: включён.
- Duration: `${__P(duration,120)}`.
- Startup delay: 0.

## Результаты JMeter

Значения взяты из строки `Get product` таблицы Statistics в HTML-отчётах и сверены с исходными JTL-файлами. Среднее время и RPS округлены до двух знаков после запятой.

| Пользователи | Количество запросов | Throughput, RPS | Average, мс | p95, мс | Error Rate, % |
|---|---:|---:|---:|---:|---:|
| 10 | 1144 | 9.63 | 2.43 | 5 | 0 |
| 25 | 2850 | 23.98 | 1.21 | 2 | 0 |
| 50 | 5705 | 47.98 | 0.85 | 2 | 0 |

- **Throughput / RPS** — количество запросов в секунду.
- **Average** — среднее время выполнения HTTP-запроса.
- **p95** — время, за которое завершились примерно 95% запросов.
- **Error Rate** — доля неуспешных запросов, включая ошибки проверки ответа.

Пауза в 1 секунду не входит во время ответа HTTP-запроса, но влияет на частоту запросов. Метрики рассчитаны за весь запуск, включая ramp-up.

Всего выполнено 9699 запросов. Все они завершились со статусом HTTP 200 и прошли проверку. При 50 пользователях максимальное время отдельного запроса составило 38 мс, при этом p95 осталось равным 2 мс.

## Вывод по JMeter

При увеличении нагрузки с 10 до 50 пользователей throughput вырос с 9.63 до 47.98 запросов в секунду, то есть примерно в 4.98 раза. Рост почти пропорционален количеству пользователей.

Среднее время ответа составило 2.43, 1.21 и 0.85 мс, а p95 — 5, 2 и 2 мс соответственно. Во всех трёх запусках доля ошибок равна 0%.

В проведённом эксперименте признаков деградации не обнаружено: Throughput продолжал расти, увеличения среднего времени ответа и p95 не было. Момент, когда Throughput перестал бы расти, а задержки или число ошибок начали бы увеличиваться, не наблюдался. Проверенные уровни 10, 25 и 50 пользователей оставались стабильными при паузе 1 секунда.

Снижение времени ответа в последующих запусках не доказывает, что рост нагрузки ускоряет сервер. Каждый уровень проверялся одним запуском, причины различий отдельно не исследовались.

Результаты относятся к простому локальному API, который формирует ответ в памяти. Сервер и генератор нагрузки использовали ресурсы одного компьютера. Максимальная производительность сервера не определялась; полученные значения нельзя считать пределом его возможностей.

## Дополнительное задание в Gatling

В Gatling реализован тот же запрос получения товара. Сценарий находится в [ProductsSimulation.java](gatling/src/test/java/ru/itmo/testing/load/ProductsSimulation.java), настройки Maven — в [gatling/pom.xml](gatling/pom.xml).

Сценарий читает тот же `jmeter/products.csv`. Maven добавляет этот файл в тестовые ресурсы, поэтому отдельная копия CSV не нужна. Метод `circular()` повторяет чтение идентификаторов с начала файла. Перед каждым запросом выполняется пауза 1 секунда, ответ проверяется через `status().is(200)`.

Число одновременно работающих пользователей постепенно растёт от 0 до заданного значения за 10 секунд, затем удерживается до конца запуска. Общая длительность ограничена 120 секундами. Как и в JMeter, проведены отдельные запуски на 10, 25 и 50 пользователей.

Перед ними выполнена короткая проверка: 1 пользователь, ramp-up 1 секунда, ограничение длительности 10 секунд. Получено 9 успешных ответов, KO = 0. Эта проверка не включена в сравнение основных запусков.

### Результаты Gatling

Значения взяты из строки `Get product` в HTML-отчётах. Gatling показывает среднее время ответа с округлением до целых миллисекунд.

| Пользователи | Количество запросов | Throughput, RPS | Average, мс | p95, мс | Error Rate, % |
|---|---:|---:|---:|---:|---:|
| 10 | 1145 | 9.54 | 3 | 7 | 0 |
| 25 | 2855 | 23.79 | 2 | 3 | 0 |
| 50 | 5715 | 47.62 | 1 | 2 | 0 |

Всего в трёх основных запусках выполнено 9715 запросов. Все запросы прошли проверку HTTP 200, ошибок нет. В отчётах Gatling успешные запросы обозначаются как OK, неуспешные — как KO.

### Сравнение с JMeter

| Пользователи | JMeter RPS | Gatling RPS | JMeter Average, мс | Gatling Average, мс | JMeter p95, мс | Gatling p95, мс |
|---|---:|---:|---:|---:|---:|---:|
| 10 | 9.63 | 9.54 | 2.43 | 3 | 5 | 7 |
| 25 | 23.98 | 23.79 | 1.21 | 2 | 2 | 3 |
| 50 | 47.98 | 47.62 | 0.85 | 1 | 2 | 2 |

Результаты близкие: различие RPS во всех трёх случаях меньше 1%. Оба инструмента показывают рост пропускной способности почти пропорционально количеству пользователей. Доля ошибок во всех запусках равна 0%. При 50 пользователях p95 в обоих инструментах составляет 2 мс.

В JMeter сценарий собирается в графическом интерфейсе и сохраняется в `.jmx`. В Gatling запросы, паузы, проверки и профиль нагрузки описываются Java-кодом, а запуск выполняется через Maven. Оба инструмента создают HTML-отчёты с количеством запросов, RPS, временем ответа, перцентилями и ошибками.

### Вывод по сравнению

Gatling подтвердил результат JMeter: при выбранной нагрузке признаков деградации не обнаружено. С ростом числа пользователей RPS увеличивается, а p95 не растёт. Проверенные уровни 10, 25 и 50 пользователей оставались стабильными при паузе 1 секунда.

Небольшие различия времени ответа не позволяют сделать вывод, что один инструмент лучше или точнее другого. Для каждого уровня выполнено по одному запуску каждого инструмента, а среднее время в отчётах Gatling округлено до целых миллисекунд. Максимальная производительность API в этом сравнении не определялась.

## Повторный запуск

Нужны JDK 21, Apache JMeter 5.6.3 и Maven. Зависимости Gatling Maven скачает автоматически при первом запуске. В командах ниже JMeter распакован в `~/tools/apache-jmeter-5.6.3`.

### Запуск сервера

В IntelliJ IDEA открыть проект, выбрать JDK 21 и запустить метод `main` класса `ru.itmo.testing.local.LocalApiServer`.

Также сервер можно запустить из корня проекта в терминале:

```bash
java src/main/java/ru/itmo/testing/local/LocalApiServer.java
```

Для этого варианта достаточно JDK 21: дополнительные библиотеки и Maven не нужны. Во время тестирования сервер должен оставаться запущенным.

В другом терминале проверить ответ:

```bash
curl -i http://127.0.0.1:8080/api/products/1
```

Ожидаются HTTP 200 и JSON первого товара. Если порт 8080 занят, нужно остановить процесс, который его использует, прежде чем запускать сервер.

### Запуск нагрузки

Из корня проекта перейти в папку со сценарием:

```bash
cd jmeter
```

Команды ниже создают отдельную папку для повторного эксперимента. Приложенные результаты сохраняются, повторные измерения с ними не смешиваются.

```bash
run_dir=$(mktemp -d "$PWD/run.XXXXXX")

for users in 10 25 50; do
  sh ~/tools/apache-jmeter-5.6.3/bin/jmeter \
    -n -t products.jmx \
    -Jusers="$users" -Jrampup=10 -Jduration=120 \
    -l "$run_dir/users${users}.jtl" \
    -j "$run_dir/users${users}.log" \
    -e -o "$run_dir/report-users${users}" || break
done

printf 'Результаты: %s\n' "$run_dir"
```

Цикл выполняет три запуска по очереди. Каждый занимает около двух минут, после него создаётся HTML-отчёт. Параметры `-l` и `-j` задают файлы результатов и технического журнала, `-e -o` включают создание отчёта. В конце каждого запуска нужно проверить показатель `Err` в консольной сводке.

Открыть отчёт повторного запуска для 50 пользователей на macOS:

```bash
open "$run_dir/report-users50/index.html"
```

Для остановки Java-сервера использовать Stop в IDEA или Ctrl+C в терминале, где он запущен.

### Запуск Gatling

Открыть отдельный терминал в корне проекта. Java-сервер должен оставаться запущенным.

Короткая проверка:

```bash
mvn -f gatling/pom.xml gatling:test \
  -Dusers=1 -Drampup=1 -Dduration=10
```

Три основных запуска:

```bash
for users in 10 25 50; do
  mvn -f gatling/pom.xml gatling:test \
    -Dusers="$users" -Drampup=10 -Dduration=120 || break
done
```

Запуски выполняются последовательно. В итоговой статистике нужно проверить значение KO. Для каждого запуска Gatling создаёт новую папку в `gatling/reports`, сохраняет журнал `simulation.log` и HTML-отчёт `index.html`. Путь к отчёту выводится в терминал. Открыть `index.html` можно в браузере, сохранив рядом все вспомогательные файлы отчёта.
